# Architecture overview

DayMug is a single-process Go service that exposes a REST + WebSocket API and internally spawns and supervises code-CLI agent child processes (`claude` / `codex`). The frontend is a Vue 3 SPA; production builds embed it in the backend binary, so **the release artifact is a static binary with no external runtime dependencies (other than the `claude` / `codex` CLIs themselves)**.

## Top-level layout

```
DayMug/
├── backend/          Go service (Gin + SQLite)
│   ├── cmd/server/   Entry point and CLI subcommands (serve / bootstrap / upgrade / user / …)
│   └── internal/     Private implementation: config / handler / middleware / agent / service / store / imbot / prompts / userenv / …
├── frontend/         Vue 3 + TS + Vite + Tailwind + shadcn-vue (pnpm)
├── docs/             This documentation
├── scripts/          Build and local deploy scripts (build-local.sh, etc.)
├── config.example.yaml   Root config sample (see also docs/guides/config.sample.yaml)
├── AGENTS.md / CLAUDE.md Project notes for coding agents
└── FEATURES.md / README.md / RELEASING.md / docs/guides/installation.md
```

## Request lifecycle of one conversation turn

Using "a user sends a message in a conversation" as the example, across the layers:

1. **Connect**: the frontend `useWebSocket` opens `GET /api/terminal`. During `init` the server resolves the conversation's user, work_dir, provider/account, and session id.
2. **Pick a backend**: `service.BackendRegistry.For` selects the `agent.Backend` matching the conversation's provider type (claude / codex / claude-compatible / openai-compatible).
3. **Lock the cwd**: on the **first message**, `PromptRunner.LockConversationWorkDir` writes the working directory actually used back to `conversations.work_dir`; from then on it is pinned and never drifts (see [Working directory](working-directory.md)).
4. **Resolve the account + queue**: `service.ResolveConversationAccount` checks that the conversation's pinned account is still in the user's currently allowed set; `service.Pool` enforces a concurrency limit per `(account name, provider type)` and, when over the limit, pushes `queue_status` to the frontend (the number of tasks running or queued ahead).
5. **Assemble the prompt**: `service/prompt.go` renders the Agent's persona (role definition) into a system prompt and hands it to the adapter via `RunRequest.SystemPrompt`: Agent SDK uses the bridge request's `systemPrompt`, the claude CLI uses `--append-system-prompt`, codex app-server uses `developerInstructions`, and the codex CLI uses `-c developer_instructions=…`. None of them write files into the working directory.
6. **Resume or start fresh**: `applySessionToRequest` calls `Backend.SessionExists` via `service.PrepareRunSession` to probe whether the session log exists **on disk** — if so it resumes (`RunRequest.IsResume`), otherwise it is a first run (claude-family session ids are pre-generated by DayMug; codex-family backends with `AssignsSessionID` assign their own id and report it back via `system_init`).
7. **Spawn the child and stream**: the adapter parses each transport's output (CLI stream-json / SDK bridge NDJSON / app-server JSON-RPC) into the unified `agent.StreamEvent` (`Kind*` constants), and `service.Broadcaster` fans it out to every online client of that conversation (multi-tab sync).
8. **Persist**: user messages, assistant messages, thinking, errors, and usage (tokens / cost) are written to SQLite; the first user message triggers auto-titling.

## Key design trade-offs

- **The first provider is the default CLI**: the first entry in the database Provider list is the implicit default backend for new conversations; admins can reorder it on the model settings page. See the [configuration guide](../guides/configuration.md).
- **Disk-based, not DB-based, session resume**: whether to `--resume` depends on whether the CLI's own `*.jsonl` exists, not on message state in the DB — because a failed first request also leaves a log.
- **No implicit account fallback**: users not bound to a given CLI type are rejected outright rather than silently falling onto the shared `default` account (which would pile everyone onto one account and hit rate limits).
- **Layered hot reload**: `config.yaml` is still read only once at startup; providers, models, and pricing live in SQLite and take effect as soon as they are saved in the admin UI.
- **Single-tenant assumption**: `agent.Sandbox` currently has only a no-op implementation (or the optional Linux `bwrap` sandbox), and the HTTP layer's `safePath()` constrains only the API, not the spawned CLI itself. See [Multi-user](multi-user.md).
