# IM Bot Integrations (Slack / Feishu (Lark) / Telegram)

A DayMug Agent can have multiple Slack / Feishu (Lark) / Telegram bots attached (for WeChat see `docs/guides/wechat.md`). The bot handles IM transport; the Agent remains the sole chat principal. All three platforms use outbound connections only, so no public callback URL is needed: Slack uses Socket Mode, Feishu uses its event long connection, and Telegram uses Bot API long polling (`getUpdates`).

## Agents and attached bots

- The Agent is the sole chat principal and owns the name, working directory, role prompt, and web conversations.
- An Agent can have one or more bots attached; each bot maps to one Slack, Feishu, or Telegram app and holds the platform credentials, channel rules, and an optional model override.
- Every attached bot resolves to the same Agent via `agent_id`, so they share the full prompt and runtime configuration; the `user_id` of an IM conversation is also the Agent id. When a bot's `model` is non-empty it takes precedence for new threads; when empty, the Agent's default model and server configuration are inherited.
- After adding, editing, or deleting a bot on the Agent edit page, the connector hot-reloads: only bots whose credentials / platform / enabled switch changed reconnect, and other bots' connections are unaffected (channel rule changes take effect immediately without reconnecting). The page shows each bot's connection status.
- A bot whose connection fails (e.g. bad credentials, network blips) or drops while running retries automatically with exponential backoff (starting at 5 seconds, capped at once every 5 minutes); the failure reason is shown in the bot status.

## Message and session flow

```text
Slack / Feishu / Telegram ─outbound conn→ imbot.Manager (dedup, inject AgentID/BotID)
                         ↓
                  imbridge.IMBridge (bot rule gating)
                         ↓
       service.Pool + agent.Backend (shared account concurrency pool)
                         ↓
           bot_threads: IM thread → Agent conversation + CLI session
                         ↓
              ┌──────────┴──────────┐
              ↓                     ↓
   update IM progress message   DayMug WebSocket live stream
```

- A top-level message automatically becomes the root of a new thread, and all replies stay inside that thread.
- When an @ in a Slack thread / Feishu thread first creates a DayMug conversation, the thread history before the triggering message is read, injected into this Agent prompt, and saved, and then the current @ message is saved. Afterwards, even if `require_mention` keeps messages that don't @ the bot silent, the next @ to the bot resumes from the persisted sync cursor and back-fills and injects those messages; already-synced messages and the bot's own saved replies are not imported again. In Feishu, root messages sent by other apps or webhooks are read only as context and do not trigger an Agent run.
- Back-filled thread history is **stored in full** (the web history stays complete), but the window injected into the prompt is bounded: at most 20 messages and 24000 bytes total, with any single message over 4000 bytes truncated on a rune boundary. The newest messages are kept (short follow-ups like "take a look at this" refer to exactly those), and the dropped older messages are summarized in one line, `(N older message(s) omitted…)`, pointing to the full DayMug conversation. Unbounded injection is expensive in two shapes: a thread idle for hours back-fills the whole gap at once; and when two bots relay to each other, every `[HANDOFF]` re-stuffs the other side's full progress narrative.
- Each Slack thread / Feishu thread maps by default to one DayMug conversation under its Agent; the same thread keeps using the provider, model, and CLI session chosen at creation. A bot can set `max_conversation_duration` (default `12h`, or any Go duration such as `3h`): the window is fixed from the conversation's first message, and later messages don't extend the deadline; the first message after the boundary creates a new DayMug conversation and CLI session under the same platform thread, using the bot's model configuration at that time. Leaving it empty also uses the default `12h`; only an explicit `0` means reuse forever. Telegram / WeChat apply the same split rule at their own chat or topic granularity.
- **Telegram sessions are per chat**: a private chat and an ordinary group are each one conversation; a supergroup with Topics (forum) enabled gets one conversation per topic. A Telegram "reply to message" only exposes the direct parent and cannot walk the whole chain; forking sessions on it would land the same conversation in different sessions depending on which message the user replied to, so replies don't fork sessions and are only used to decide whether the message is addressed to the bot.
- The Telegram Bot API offers no way to read message history, so there is no thread-history back-fill: the session starts at the triggering message, and later context comes from DayMug's own persisted records. Slack / Feishu back-fill is unaffected.
- When a bot creates a conversation it first uses "platform · channel" as a fallback title; once the first message is saved and a summary is generated, the same auto-naming flow as web Agent conversations replaces the fallback title with the message summary.
- IM user messages, thinking, tool calls, streamed text, and final replies use the same persistence and WebSocket events as web chat. The web UI can open the conversation mid-run or reload the full history after a refresh; user messages from group chats keep the platform sender identity, so multiple members in one thread show up under their own Slack / Feishu names.
- If a conversation was originally created from a Slack thread / Feishu thread, user messages later sent from DayMug `/chat` are also appended to the original thread tagged `DayMug Web`; the Agent's progress placeholder, final reply, and failure or cancellation status are mirrored back to that thread as well. Web and IM inbound share one thread lock, so the two entry points never run the same CLI session at once. Ordinary new web conversations never send anything to any IM platform.
- All outbound platform messages may only be sent by the current attached bot's connector. On startup Slack rejects employee user tokens via `auth.test.bot_id`; IM Agents are also forbidden from calling Slack / Feishu message tools, APIs, CLIs, webhooks, or MCP themselves to bypass the bot identity.
- Web submissions stay serialized within a thread; when Slack / Feishu receives a new triggering message for the same bot in the same thread, it immediately cancels that bot's previous turn (whether it came from IM or the web) and handles the latest message. The preemption key includes the Agent and bot identity, so other bots in the same platform thread are not cancelled. Different threads run in parallel; IM, web, and the HTTP API share the `max_concurrent` limit.

## Configuration entry point

Settings → New Agent → open the Agent edit page → Attached bots: add multiple Slack / Feishu / Telegram / WeChat connections and set each one's model, maximum conversation duration, credentials, rules, and switches. An empty model uses the Agent/server configuration; the maximum conversation duration defaults to `12h`, an empty value is still treated as `12h`, and `0` means unlimited. The question mark next to the attached-bots section and the channel-rules heading opens the full configuration guide, covering every connection field, the fixed conversation window, channel rules, and refusal replies.

The bot edit form shows the permissions the platform requires. After entering credentials, click "Test connection" to check each item: Slack verifies the Bot Token identity, the App-Level Token's Socket Mode capability, and all Bot Token Scopes; Feishu verifies the app credentials, bot capability, and permission grant status; Telegram verifies the token identity, confirms no webhook is blocking long polling, and reports the current state of the two @BotFather switches. The test is read-only: it does not save the bot configuration or send anything to a channel or group.

### Slack app setup

1. Create an app at <https://api.slack.com/apps>, enable Socket Mode, and generate an `xapp-` App-Level Token with `connections:write`.
2. Bot Token Scopes: `app_mentions:read`, `chat:write`, `channels:history`, `groups:history`, `im:history`, `users:read`; add `files:read` to receive images or files and `files:write` to send Agent artifacts.
3. Subscribe to `app_mention`, `message.channels`, `message.groups`, `message.im`.
4. Install the app to get the `xoxb-` Bot Token, and add the bot to the target channels.

### Feishu app setup

1. Create a custom enterprise app on the Feishu Open Platform and enable the bot capability.
2. Request `im:message`, `im:message:send_as_bot`, and `im:resource` (receive, send, recall progress cards, upload images or files); request `im:message.group_msg` as needed to read group messages. Feishu's recall API accepts any one of `im:message`, `im:message:send_as_bot`, `im:message:recall`; the admin connection test shows the recall capability separately but does not require a duplicate grant. Optionally request read-only contacts user info permission (e.g. `contact:user.base:readonly`): once granted, group chat records show sender names; otherwise they fall back to open_id.
3. Subscribe to `im.message.receive_v1` via the long connection.
4. Publish a version, get it approved, and add the bot to the target groups.

### Telegram app setup

1. In Telegram, message [@BotFather](https://t.me/BotFather) and run `/newbot` to get a Bot Token of the form `123456789:AA…`. Telegram has no scope system; this one token is enough to send and receive messages.
2. **Disable group privacy mode**: `/setprivacy` → pick the bot → `Disable`. When enabled (the default), Telegram only delivers commands, messages that @ this bot, and replies to this bot's messages — that already covers everything `require_mention: true` needs, but `auto_reply` channels require privacy mode off to receive all messages.
3. If the bot previously had a webhook set, delete it with `deleteWebhook` first: webhooks and long polling are mutually exclusive, and a leftover webhook makes `getUpdates` keep returning 409, which shows up as "connected but receives no messages". "Test connection" reports this explicitly.
4. Add the bot to the target group; to isolate sessions per topic, enable Topics (forum mode) in the group settings.

> On connect, DayMug first discards the update backlog on the Telegram side. Telegram retains unfetched messages for 24 hours; without discarding them, every restart would answer day-old messages as if they were new — neither Slack's nor Feishu's long connection replays messages from the disconnected period, so this aligns the semantics across the three platforms. The cost is that messages received while the service is restarting are not answered later.

## Channel rules

Each bot has its own JSON rule array:

```json
[
  {
    "channel": "C0123456789",
    "require_mention": true,
    "allowed_user_ids": ["U0123456789", "U0987654321"],
    "extra_prompt": "This channel is the ops alerting group; keep answers brief"
  },
  {
    "channel": "*",
    "auto_reply": true
  },
  {
    "channel": "dm",
    "enabled": false
  }
]
```

| Field | Default | Description |
|------|------|------|
| `platform` | Current bot | Optional; filled in with the current bot's platform on save; cannot cross platforms |
| `channel` | Required | Exact channel id; `"*"` matches all group channels, `"dm"` matches all private chats. Slack uses `C…`/`G…`, Feishu `oc_…`, Telegram the numeric chat id (negative for supergroups, e.g. `-1001234567890`) |
| `enabled` | `true` | Disables the rule while keeping its configuration |
| `require_mention` | `true` | In group chats the bot must be @-mentioned to respond |
| `auto_reply` | `false` | Responds to every message in the channel; takes precedence over `require_mention` |
| `allowed_user_ids` | — | Optional allowlist of human senders; use platform user IDs, or `"*"` to allow everyone; members not on the list cannot trigger the Agent |
| `extra_prompt` | — | System prompt appended for this channel |
| `agent_id` | — | Must not be set; messages always route to the bot's own Agent |
| `ack` | — | Deprecated and ignored; an updatable progress message is always created |
| `allow_bot_mentions` | `false` | Lets other bots' @ messages trigger this bot (bot relay) |
| `bot_mention_limit` | `3` | Number of bot triggers allowed per thread within the sliding window; `0` forbids them entirely |
| `bot_mention_window_minutes` | `30` | Length of the sliding window for the above count (minutes) |

Match priority: exact channel id → `dm` / `*`. An exact disabled rule can override `*`. **If no rule matches, the Agent does not run** — group chats and private chats alike.

Each bot's admin edit section also provides two configurable messages:

- `unconfigured_reply`: sent when a human explicitly @-mentions the bot in a group chat not covered by any rule, or messages the bot directly. Default: `🙇 Sorry, I haven't been enabled in this conversation yet, so I can't reply to your message for now.`
- `unauthorized_reply`: sent when a human outside `allowed_user_ids` explicitly @-mentions the bot or messages it directly. Default: `🙇 Sorry, I can't reply to your message for now`

Neither notice starts the Agent, creates a conversation, or consumes account-pool concurrency. Ordinary group messages that don't @ the bot stay silent; messages sent by bots also never get these notices, to avoid bots replying to each other. A rule explicitly set to `enabled: false` is likewise silent, because the admin deliberately turned that conversation off.

> ⚠️ Bots without an enabled `dm` rule have private chats disabled: messages only get `unconfigured_reply`, the Agent does not run, and the server log states the reason (`has no enabled "dm" channel rule`). New WeChat bots default to `[{ "channel": "dm", "allowed_user_ids": ["*"] }]`, letting every WeChat user talk to it; to restrict it to yourself, replace `"*"` with the actual user ID:
>
> ```json
> [{ "channel": "dm", "allowed_user_ids": ["U0123456789"] }]
> ```

With `require_mention` enabled, every group chat message must explicitly @ the bot, including replies in a thread already bound to a DayMug conversation. Only `auto_reply` overrides this; private chats are not subject to `require_mention`.

With a non-empty `allowed_user_ids`, only the platform user IDs on the list can trigger that channel rule; `"*"` in the list allows everyone. This allowlist takes precedence over `require_mention` and `auto_reply`: unlisted members never run the Agent; an explicit @ to the bot or a direct message returns `unauthorized_reply`, while ordinary non-@ messages in auto-reply channels stay silent. An empty array, an omitted field, or a list containing `"*"` all mean human senders are unrestricted; bot relay is still controlled separately by `allow_bot_mentions`.

## @-mentioning people in replies (Slack / Feishu)

When the Agent's answer needs to actually ping someone, it writes `@` + that person's display name in this thread (i.e. the name used in the prompt's `[name]:` prefix or `@name`), and DayMug converts it to a native platform mention when sending the final answer: Slack `<@U…>`, Feishu card `<at id="ou_…"></at>`. This is the inverse of the inbound direction — inbound turns `<@U0123>` into `@name`, outbound turns it back.

- **Only people seen in this thread are recognized.** The directory is fed by inbound messages DayMug itself observed: the sender of the triggering message, senders in the back-filled thread history, and people @-mentioned in messages. People who never appeared in this thread, `@channel` / `@here` / `@everyone`, and mention markup the Agent assembles itself are all unresolvable and are shown literally.
- **Bots are not in the directory.** Otherwise an `@Reviewer` in ordinary body text could trigger the other bot, bypassing the deliberately designed `[HANDOFF @Bot]` protocol. Slack decides via `is_bot` from `users.info`; any id that can't be looked up is treated as a bot (fail closed).
- **Only resolved in the final answer.** Progress messages are edits, and neither Slack nor Feishu notifies for mentions added by an edit — which is also why the final answer is sent as a new message.
- **Each person is @-mentioned only once.** When sending the final answer, DayMug prepends a native mention of the requester; if the Agent already wrote the requester's name in the body (the prompt teaches it to, and the prefix DayMug added last turn is restored to `@name` in the back-filled history, so the model readily copies it), the prefix is not added again — two mentions pointing at the same id produce only one notification, and the duplicate is just visual noise. The same mention repeated back to back (`@name @name`) is also collapsed into one; same-name mentions on different lines are treated as normal body text and not collapsed.
- **Write the full name.** Matching is against the complete display name, preferring the longest match: if the display name is `Mary Jane Smith`, writing only `@Mary Jane` won't match. A name may be followed directly by CJK text, but not by an ASCII letter or digit — otherwise `@Mar` would steal `@Mary`. `` `@name` `` inside inline code or a code block is only a reference and won't ping.
- Telegram's `@username` is already plain text and doesn't go through this path; WeChat is not supported.

## Bot relay (bots @-mentioning each other)

An Agent's reply can hand the thread over to another bot in the same workspace — the typical case: coding bot A finishes a task and hands review to bot B. DayMug adds to A's system prompt the names of targets that are currently online, on the same platform, and have `allow_bot_mentions` enabled in the current channel.

- **Outbound protocol**: a relay happens only if the last non-empty line of A's final reply strictly follows the `[HANDOFF @BotName] instruction` format, e.g. `[HANDOFF @Reviewer] Please review this implementation`. `@Reviewer` in ordinary body text, quotes, or code never triggers it. DayMug re-validates the target when sending, requiring the name to match uniquely and the target to still be online, on the same platform, and allowing bot mentions in the current channel; otherwise it skips and logs. When no relay is needed, the Agent outputs no `HANDOFF` line.
- **Native message**: after validation, DayMug appends a native mention message carrying the actual task in the same thread under A's identity, e.g. `@Reviewer Please review this implementation`. Slack uses `<@U…>`, Feishu uses `<at user_id="ou_…">Bot name</at>`, and Telegram uses plain `@username`; on all three platforms the visible message does not repeat A's answer.
- **Inbound**: triggers only when B's rule for the channel has `allow_bot_mentions` enabled **and the handoff explicitly @-mentions B** (bot messages never qualify for `auto_reply` or the "linked thread needs no @" exemption, and bot messages in private chats are always ignored). On Slack it arrives via the platform's bot message event; Feishu's receive-message event excludes messages sent by bots, and a Telegram bot likewise never receives another bot's messages, so on those two platforms DayMug delivers the same handoff directly to B after A successfully sends the visible native @ message. On all three platforms the run maps to a separate conversation under B's own Agent; `spawn_agent` is never called inside A's Codex session in place of B.
- **Circuit breaker**: each thread allows at most `bot_mention_limit` bot triggers within the sliding window (default 3 per 30 minutes, configured per channel rule); beyond that, triggers are dropped and a "limit reached, please intervene manually" notice is posted at most once per window. Human messages are unrestricted and don't consume the quota; the window resets on restart.
- **Context**: on all three platforms, non-@ human messages in the same thread received since the relayed bot last responded are added to the next turn's context. Slack prefers syncing the full thread history from the platform; Feishu and Telegram internal relays use a bounded thread cache DayMug maintains after rule and sender-allowlist checks, and carry both the task instruction and A's full reply. So human additions made while A is running reach B, and when B hands back to A they reach A too.
- **A relay turn doesn't re-inject the other side's messages**: in the turn triggered by `[HANDOFF]`, **the other Agent's own messages in the back-fill are kept out of the prompt** — the `[HANDOFF]` instruction itself is the request; pasting the other side's full progress narrative again puts the same content in twice, and it stays in the receiver's CLI session to be re-read every later turn. Human messages are still injected in full (`[HANDOFF]` can't restate what others said). The number omitted is noted in one line at the top of the context; **the database and web UI still keep the full conversation**. Therefore a `[HANDOFF]` instruction must be self-contained: state the goal, identifiers, and exact requirements, and don't write "as above" — the receiver has no "above". The cache only covers messages DayMug actually received: Telegram groups must disable privacy mode as described in "app setup", or the platform won't deliver non-@ messages to any bot; cached messages not yet imported by some Agent turn before a service restart cannot be recovered. The two Agents can keep separate working directories and read a knowledge base or deliverables in a shared parent directory via absolute paths. When B needs rework, it uses the same strict protocol, e.g. `[HANDOFF @Coder] Please rework per the review comments`, forming a round-trip loop bounded by the circuit breaker.

## Progress display

- Slack: first posts a placeholder message in the thread and shows "bot name + is typing…" under the input box via `assistant.threads.setStatus`; once the agent thinking stream arrives, `chat.update` shows the thinking content in place, throttled; once the reply starts generating, the same message keeps showing a throttled live preview of the body text, CJK included. When the task succeeds, `chat.delete` first deletes the progress message, then a new message with the full answer @-mentioning the requester is sent so Slack produces a new-message notification; deletion shares the `chat:write` scope with sending, and the admin connection test shows the `chat:delete` capability separately. Markdown in the reply (bold, links, headings, strikethrough) is converted to Slack's mrkdwn dialect; inline code and code blocks are kept as is. The conversion order is "first escape `&`, `<`, `>` in the body to HTML entities, then insert DayMug's own generated mrkdwn markup", so `<!channel>` and `<@U0123>` in the Agent's body are shown literally and never become a real everyone-ping or mention (Slack parses these three control characters across the whole message, and code blocks only suppress styling, not this parsing layer, so they are escaped inside code blocks too and Slack restores them on display). The Agent can only @ people via the "@-mentioning people in replies" directory above, never by assembling mention markup itself.
- Feishu: first replies in the thread with an `interactive` markdown card, then shows thinking content and later status in place, throttled, via message patch. When the task succeeds, the progress card is recalled first, then a new card with the full answer @-mentioning the requester is sent; the admin connection test shows the `im:message:recall` recall capability separately (the already required `im:message` or `im:message:send_as_bot` also covers it).
- Telegram: first sends a placeholder via `sendMessage`, refreshes it in place, throttled, with `editMessageText`, and finally updates it to the full answer; meanwhile `sendChatAction` shows "typing" (it expires on Telegram's side after about 5 seconds and can't and needn't be cleared; `telegramTypingHeartbeat` resends it every 4 seconds to keep it alive — see the next item). Outbound always uses `parse_mode=HTML` rather than MarkdownV2: MarkdownV2 requires escaping 18 characters in the body one by one, and a single stray `*` or `_` in Agent output (very common in code and path globs) makes Telegram reject the whole message with a 400; HTML mode has only three control characters, `&`, `<`, `>`, and, like Slack, uses the order "escape the body first, then insert DayMug's own generated markup", so HTML in the Agent's body is shown literally. An unclosed ``` caused by code block truncation gets its closing tag added automatically, so the whole reply isn't rejected for unbalanced tags. Telegram returns 400 `message is not modified` for edits that don't change content; this is normal (progress throttling doesn't diff the body), and DayMug treats it as success instead of aborting the turn.
- **Self-expiring typing indicators are kept alive by a heartbeat, not by riding agent events.** Progress refreshes are throttled to 3 seconds and only happen when the stream actually produces something: a long tool call can go tens of seconds with zero events, and the typing indicator would go dark midway — exactly when the reader most needs to know it's "still running". `progressResponder.activityInterval` lets the connector run its own independent clock: WeChat 5 seconds (`wechatTypingHeartbeat`), Telegram 4 seconds (`telegramTypingHeartbeat`, which must be shorter than the platform's ~5-second expiry window). **Slack deliberately has no heartbeat**: `assistant.threads.setStatus` is a persistent status with an explicit clear, and resending it only wastes quota. Heartbeats serve only self-expiring indicators.
- The heartbeat is wound down by `imbot.TurnCloser`; `IMBridge.HandleMessage` `defer`-closes the responder on every exit — including rule rejection and run failure, paths that never reach `Complete`.
- The progress message layout is fixed as "status banner on the first line → `[Reasoning]` section → `[Reply]` section". Both sections are shown together in a fixed order: thinking and reply are two independently accumulating streams, and rendering "whichever arrived last" would make the reader see two unrelated pieces of text keep swapping in the same message. With only one stream, no subheadings are added (the banner already states the current phase). The streamer clears the thinking buffer every time it persists a result, so the progress side caches the last non-empty reasoning to keep the reasoning section from flickering out mid-turn in a multi-result turn.
- Thinking and reply body previews refresh at most every 3 seconds (both share one throttle clock); phase changes such as tool calls and wrap-up refresh immediately once. The two sections share a budget of about 3200 characters, with the reply section taking at most 2000 and the rest left for reasoning (before the reply starts, reasoning can use the full 3200); each keeps its most recent content to stay under platform message limits. Thinking content is shown only when the backend actually emits `thinking_delta`; models without a thinking stream still show the plain "thinking" status.
- **New threads round-robin across the Agent's accounts.** A bot picks only one default model; if every turn used the default binding, other accounts offering the same model would sit idle while the default account first queues and then gets rate-limited. When a new thread opens, accounts that are "authorized + `models` includes this turn's model + that model is not in rate-limit cooldown" are round-robined; the chosen account is written to `conversations.account_name`, and every later turn in that thread stays on that account (the CLI session lives in that account's config dir, so switching accounts would break resume). Details in `docs/architecture/multi-user.md`.
- IM tasks and web tasks enter the same account concurrency pool. When an account's `max_concurrent` limit is exceeded, the status shows "I'm currently queued, N task(s) ahead of me"; each time a task ahead completes or is cancelled and the queue position drops, the Slack message or Feishu card updates immediately and `queue_status` is broadcast to the corresponding DayMug conversation.
- Queue position, run failure, and cancellation-by-new-message text go through `imbot.Notify` (`NoticeResponder`) rather than `Update`: they must not be overwritten by the later answer, so on platforms without an edit primitive (WeChat) they have to be sent as new messages, or the reader sees only silence. On platforms that can edit, the two are equivalent. Details in `docs/guides/wechat.md`.
- While queued, the task also counts as the conversation's running task and can be cancelled from the DayMug web UI; once it gets an execution slot, the status switches to "thinking". When the web UI cancels an IM task that's still queued, the IM side receives "cancelled while queued" rather than "timed out waiting for an idle account" — both show up as the wait context being invalidated, but reporting the user's own cancellation as a timeout effectively tells them to retry something they just deliberately stopped.
- Long answers are split into chunks of about 3800 characters, at most 10 chunks; Slack and Feishu first delete the original progress message, then reply with all chunks as new messages in the same thread (Feishu chunks all use markdown cards).

### How queued IM messages appear in the web UI

IM messages are persisted with `queue_status = 'pool_queued'` (`store.QueueStatusPoolQueued`); when a slot is acquired, `imRun.leaveQueue` clears it and broadcasts `prompt_started`. This solves three things:

- **The semantics of `prompt_started` are aligned.** On the web path it means "this prompt has started running" (`prompt_runner` sends it only after acquiring a slot). Sending it at persistence time would make a queued IM task look like it was already running in the web UI: the chat view would promote the message from the staging area to an ordinary sent bubble, and the queue card and position would never appear.
- **The state survives a refresh.** `queue_status` comes back with REST, so the most common order — "send a message from WeChat, then open the web UI" — also shows the queue card; the `queue_status` frame is live and not in the replay buffer, so it alone can't cover tabs opened later.
- **It's invisible to the web prompt queue.** Every dispatcher query matches `'pending'` / `'processing'` exactly, so `PeekNextPendingPrompt` won't claim and rerun it, `DeletePendingPrompt(s)` won't delete rows sent by IM users, and `ResetProcessingToPending` won't revive it. **Don't mark it `'pending'` for convenience** — that would make the web dispatcher run the same message again.

The frontend marks this card `fromIM` (`chatQueueStore.PendingPrompt`): its × is **not** "recall and edit" but cancels the whole turn. Text typed in WeChat can't be "recalled" into the web input box, and this row isn't in the dispatcher's pending set, so the per-item recall API can't even find it.

IM tasks don't survive a restart (connector, pool ticket, and agent process are all gone), so `IMBridge.ClearStaleQueuedPrompts` clears leftover markers on startup; otherwise a queue card would linger with nobody waiting on it.

## Case mode

A switch in Agent settings, off by default. When on, **all** of that Agent's IM bots use case mode; conversations not bound to an IM channel (web conversations) are unaffected — both conditions are required.

It addresses threads that grow so long their context breaks down. The approach is to move the thread's persistent state out of the conversation history into a bounded document:

- **The case file is keyed by `(channel_id, thread_id)`**, without the agent — multiple Agents in the same thread read and write the same file, so handoffs pass state rather than transcripts. Table: `thread_cases`; every change goes into `thread_case_history`.
- **It lands in the Agent-specific directory `<owner home dir>/.daymug/agents/<agent id>/case/<channel>-<thread>.md`** (the absolute path is written into the prompt); the Agent reads and writes it with ordinary file tools, needing no extra capability, and humans can open and edit it directly. Three sibling marker files with the same name record which version the local copy was synced from (`.version`), whether the previous turn's write failed (`.unsaved`), and whether the previous turn's changes were rejected (`.rejected`). It lives under the home directory rather than the conversation's working directory so that every project doesn't grow an extra `.daymug/`; splitting by agent id preserves the existing isolation between Agents.
- **Human edits are adopted**: at the start of the next turn, if the local copy is ahead of the synced version, the edit is promoted to a new version and written back to the store, where the other Agent in the same thread can also read it. If the store has already been advanced by the other side (and the local copy is merely stale), the store wins.
- **A failed write doesn't masquerade as a human edit**: a turn where `SaveThreadCase` fails leaves `.unsaved`, and the next turn replays it under **the Agent's own name** rather than recording it as `human`. This matters — human editing is the strongest correction mechanism in this design, and if every SQLITE_BUSY poured an entry into `updated_by=human`, real human edits would be drowned out. When the first turn's write fails, the local copy is also not overwritten by the template; otherwise what's lost is not one version but the entire case file.
- **Dropped "ruled out" entries are restored, not rolled back wholesale**: the platform re-appends missing entries to that section, and the Agent's other changes in the turn are saved as usual. Placeholder lines (`None yet`, `none`, `None`) don't count as entries and can be replaced by real ones — protecting them as entries would make them undeletable, and the turn that deleted one would have its entire change voided. Only "section structure drifted" still rejects the whole file, and only when the previous version's structure was compliant; historical case files that already drifted are allowed to migrate step by step, otherwise they would never converge.
- **Rejections are reported to the Agent**: the rollback reason is written into `.rejected` and appended to the end of the user message on the next turn. Without it, the Agent only sees its changes vanish, and the cheapest reaction is to write the same thing again and waste another turn.
- **Session rotation is decided by the platform from the measured watermark**: when `conversations.last_context_usage` exceeds 70% of the window, the next turn cuts the conversation / session / provider / model (reusing the conversation-expiry path) and restarts from the case file. 70% rather than hitting the wall leaves the Agent room to write the case file properly. The ratio is configurable via `case_rotate_context_ratio` (see `docs/guides/configuration.md`).
  This watermark comes from the provider's own token accounting; the web and IM paths each write it into `last_context_usage` (`PromptRunner.broadcast` / `IMBridge.broadcastIM`). The decision reads this column, not the live in-memory frame — so when adding a new stream exit to the IM path, missing this interception raises no error at all; it just means rotation never fires, while the context progress bar on the page keeps displaying normally.
- **Limits are enforced in code**: a soft limit of 8k tokens prompts compression, and at the hard limit of 12k the first instruction is "delete until back under the limit first". Models only append and never delete, so this can't live only in the prompt.
- **Exceeding the watermark means "may rotate", not "must rotate"**: there is one more admission check before actually dropping the session (`imRun.admitRotation`). If the case file is still an empty template, or its `updated_at` is earlier than the `created_at` of the conversation being retired, it hasn't yet absorbed what that session learned, so the platform **keeps the session without rotating** and appends a note to the end of the user message telling the Agent why the context is full and that writing the case file is what unblocks it. This gate isn't optional politeness: after rotation the thread history is not replayed (`LastMessageID` is deliberately kept), and Slack back-fill filters out the bot's own messages via `history.User == botUserID`, so a wrong rotation leaves the whole turn's work unrecoverable from anywhere.
  Not rotating has a cost (the next turn starts from a full context), so it's capped: above `casefile.RotateForceRatio` (0.92) rotation is unconditional — a session too full to run is worse than a lossy rotation.
- **On rotation, the retired session's last reply is carried into the new session** (`store.LatestAssistantMessage` → `casefile.HandoverPrompt`, tail-truncated to 2000 characters, system prompt only). The case file carries state, but not "the text the user is replying to": a follow-up like "not this one, check the others yourself" refers to message text, not case-file entries, and that text is nowhere to be found in the new session after rotation. It is injected as a separate block, explicitly labeled "not the case file, don't copy into the case file".
- **The rotated new session reuses the old title with a number instead of regenerating a summary** (`rotatedConversationTitle`): the first session of a thread is unnumbered, then "X" → "X-2" → "X-3"…, so the sessions of one thread link up at a glance in the web UI, and one title-model call is saved. The number isn't guessed from the title; it's derived by counting the chain back along `conversations.rotated_from` (the new session points to the old one it replaced), so a summary ending in a digit ("COVID-19" → "COVID-19-2") or a manual rename doesn't throw it off. If the old session hasn't gotten a real title yet (still a fallback title like `Slack · channel`), the new session starts as "fallback title-N", and the `-N` suffix is kept after the auto title is generated.
- **The full case file is injected into the system prompt only when starting a new session**; continuation turns include none of it. The case file is a document rewritten every turn, and both adapters render the system prompt at the very front of the prompt (codex's `developer_instructions` is the first developer message, claude uses `--append-system-prompt`) — re-injecting it every turn swaps out the prefix every turn, invalidating the cache for the entire conversation after it. If a continuation turn exceeds the limit, only a one-line hint of a few dozen tokens is appended **at the end of the user message**, positioned last so it affects no cache.

- **Exempt from the per-turn usage reminder**: case-mode IM turns don't count model requests, tool calls, or cost (`imRun.unboundedTurn`), and later messages don't receive that reminder. The decision follows the Agent's switch, not whether the case directory resolved successfully. See `guardrails` in `docs/guides/configuration.md`.

Any failing step degrades without blocking: if the case file can't be read or written to disk, that turn simply has no case-file prompt block; the turn doesn't fail.

## Images, files, and limits

- Slack and Feishu inbound both support images and ordinary files. A single Slack message can carry text plus multiple attachments; Feishu supports standalone image and file events as well as multiple images in rich text (post). Rich-text links expand to `text (URL)`, and @-mentions of others are inlined as `@name`; interactive cards in thread history have their title, body, and Markdown extracted as context. Slack downloads private files with the Bot Token; Feishu downloads via the message resource API.
- Inbound attachments are limited to 25 MiB and written by source platform into the Agent-specific directory `<owner home dir>/.daymug/agents/<agent id>/slack/`, `…/feishu/` (unknown platforms land in `…/im/`), after which the **absolute path** is handed to the Agent. Web uploads go to `…/uploads/` under the same scope, so the two never share a directory. Attachments declared as images have their real MIME type verified; ordinary files keep their sanitized filename and extension. The web UI displays persisted inbound attachments via the access-controlled `/api/users/:id/files/read` URL.
- To publish an artifact, the Agent outputs a standalone `[DAYMUG_ARTIFACT path]` line at the end of its final reply; the path may be relative or absolute, but once resolved it must be an existing, non-empty regular file inside the Agent's working directory. **There is no size limit at parse time**: this step runs before it's known which channel the turn uses, so any single number would be wrong for every channel (web replies don't upload at all; the file is served by path from local disk). Size is judged by each connector against its own platform limit. DayMug strips the protocol line, and the attached bot uploads the file to the original Slack thread / Feishu thread; the Agent never touches platform credentials.
- The web UI only displays PNG, JPEG, GIF, WebP, and BMP images generated by the Agent, not ordinary files it generates. Web-initiated conversations bound to an IM thread still upload the images or files the Agent declares to the corresponding Slack / Feishu thread.
- At most 10 Agent artifacts are published per turn. The per-file outbound limit is judged by each connector for its own platform: Slack 1 GiB (external upload streams straight from disk, no local buffering), Feishu 30 MiB, Telegram 50 MiB (the `sendDocument` multipart goes entirely into memory, the only place where the limit also bounds local memory), WeChat 25 MiB (the upload handshake requires the plaintext MD5 and ciphertext length up front, so the whole file must be in memory). Feishu's image upload API has an additional 10 MiB limit; images above it are sent as ordinary files, which doesn't count as a failure.
- When an artifact doesn't reach the reader — whether the platform rejected the upload or the marker never resolved to a file (path doesn't exist, escapes the working directory, more than 10) — a `⚠️ N file(s) could not be delivered` notice is appended, listing file names/marker paths and reasons. This notice is necessary: the reply above almost always talks about these files as if they were delivered, and the Agent itself can't see the drop, so it would just resend the same bad marker again and again. The notice only contains paths the Agent itself wrote and a plain-language reason; resolved absolute host paths go only into the server log.
- Each channel reports once, with no duplication: the one in the IM thread is appended by the bridge after upload; the one for marker resolution failures is written by the stream layer as a persisted `error` message line, so pure web conversations (no attached bot) see it too, and it survives a refresh. Upload failures only happen on the IM side, so they only produce the thread notice.
- Pure image or pure file messages in a `require_mention` channel can't carry an @, so they need `auto_reply`; on Slack the same message can include text with an @.
- In group chat messages, the @bot placeholder is stripped; @-mentions of others are replaced with `@name` so the agent knows who the message is addressed to. Telegram @-mentions are already plain `@username`, so only the bot's own handle is stripped and the rest is kept as is. Slack and Feishu behave the same, and live messages and thread-history back-fill follow the same rules; when a name can't be resolved it falls back to `@user id` (Slack `@U0123`, Feishu `@ou_xxx`), never leaving raw `<@U0123>` markup for the agent. Non-user Slack markup such as `<!here>` and `<#C123|general>` is kept as is.
- Slack alert cards (AWS Chatbot / Amazon Q, Sentry, GitHub, etc.) often have empty `text`, with all content hanging off the attachment's Block Kit. When `text` is empty, DayMug flattens blocks and attachments into plain text (section / header / context / fields / rich text; interactive elements such as buttons are skipped), for both live messages and thread-history back-fill; when `text` is non-empty, `text` wins, so attachments such as link previews aren't duplicated into the body.
- Telegram inbound supports images, documents, video, audio, and voice; for images, the largest size in Telegram's pre-scaled ladder is used. The file path is resolved via `getFile` only at actual download time — paths expire after about 1 hour, and resolving one while the message waits in the queue behind a long task would yield a dead URL. The Bot API download limit is 20 MiB, and outbound `sendDocument` is capped at 50 MiB. Outbound artifacts always go through `sendDocument`: `sendPhoto` re-encodes and compresses, and screenshots or charts the Agent generates as evidence must not be silently degraded.
- Messages are deduplicated by platform + agent + bot + message id, and the bot's own messages are filtered out. A single run has no overall wall-clock limit by default; the CLI liveness watchdog and manual cancellation are the backstop, and a hard limit can be set with `im_run_timeout`. Queue waiting has a separate 30-minute limit.
- Feishu events don't carry the sender's display name; once read-only contacts permission is granted, it's resolved via the contact API (cached); without it, it falls back to open_id.
